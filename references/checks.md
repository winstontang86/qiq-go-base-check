# 基础质量、逻辑与运行诊断检查

## 1. 编译构建

- 先识别仓库语言、工作区、模块、build tags、CGO、代码生成、目标平台、服务发布入口及 CI 参数；优先使用仓库实际命令，经说明和确认后运行。
- 对每个受影响服务执行真实发布构建所需的编译步骤。Go 多模块按 `go.work`/`go.mod` 分别定位；不要仅在根目录执行一次 `go build ./...` 就假定所有服务通过。
- 没有已定义入口时，在确认 Go 构建条件后以模块级 `go build ./...` 作为基础编译验证，并说明其与发布构建的差异；需其他 tag/平台构建的服务必须补齐。
- 依赖升级、协议/生成代码变更、公共库变更扩展到直接及传递消费者；检查生成产物是否同步，禁止在审查期间隐式覆盖用户文件。
- 保留工作目录、命令、参数、工具版本、代码快照、开始/结束时间、退出码和脱敏失败摘要。保存真实进程退出码，不使用管道最后一个过滤命令的退出码冒充构建成功。
- 缺工具、依赖、网络或环境导致未验证，记 `UNKNOWN`；退出码非零记 `FAIL`。严禁跳过失败服务、修改构建脚本掩盖问题或把 lint 成功当作构建成功。

## 2. 自动化测试与新增代码覆盖

### 执行范围

- 执行所有受影响模块的自动化测试，包括仓库要求的单元、组件和集成测试；Go 可在各模块使用 `go test -count=1 ./...`，采用仓库必需的 tags/参数，不复用过期缓存。
- 对并发变更在环境支持时补充 `go test -race`；若 race 是仓库要求或关键并发风险的必要证据，无法运行则阻断。不要将 race 成功解释为没有所有并发 bug。
- 检查测试过滤、skip、失败重试、mock、CI 矩阵和环境变量。要求的用例被跳过、只跑受影响包而遗漏受影响模块其他用例、只运行空测试文件，均不能证明通过。
- 检查测试是否能隔离真实支付、消息、网络与数据写入；使用受控测试环境，禁止在现网执行副作用测试。

### 覆盖判定

建立“新增/修改行为 → 函数/分支 → 用例 → 断言 → 执行证据”矩阵。对纯移动、机械生成、接口声明等不可执行内容给出具体理由，不以文件类型粗略豁免。

- 将新增行为和修改后引入的新分支均视为需要单测覆盖的“新代码”。至少覆盖主要成功路径、失败/边界路径；涉及权限、幂等、支付、并发时覆盖相应风险路径。
- 优先使用覆盖 profile 的文件/语句范围与 diff 相交，补充用例和断言阅读。Go 可使用 `go test -count=1 -coverprofile=PATH ./...` 及 `go tool cover -func=PATH`；必要时采用 `-coverpkg` 统计被间接调用的业务包。
- 不把模块整体覆盖率、函数被执行过、有 `_test.go` 或无断言调用视为新增行为已覆盖。Go 语句覆盖率不证明每个分支正确，需要逐行为核查断言。
- 对新增可执行行为没有有效单测设 `FAIL`；无法映射到用例或证据不完整设 `UNKNOWN`。关键新分支遗漏设 `FAIL`。
- 对修改的既有行为验证回归测试覆盖，严重 bug 修复要求存在能复现原问题、在修复后通过的用例。
- 不发明统一百分比阈值；遵循仓库已有阈值并同时检查新增行为。高总覆盖率不豁免新增代码无覆盖。

## 3. 逻辑 bug review

阅读完整函数、调用方、数据契约、错误路径和目标分支交叉变更，检查：

- 条件取反、遗漏分支、边界/空值、零值与缺省值、整数溢出、金额/精度/单位、时区、排序分页、序列化兼容性。
- 状态机与流程次序，是否先改状态再校验；重试/幂等/重复消息是否导致多次扣款、重复发放、漏处理或状态回退。
- 事务提交/回滚、错误传播、部分失败、跨服务一致性、缓存失效和回源、异步失败是否丢失业务结果。
- 并发共享状态、锁顺序、死锁、锁粒度、goroutine 生命周期、channel 关闭、context 取消、超时、资源释放、panic 和异常吞没。
- 删除/重命名、依赖升级、协议和配置变更是否破坏旧消费者；新代码与目标分支现有逻辑是否发生语义冲突。
- 校验业务不变量而非仅给出“看起来正确”。每个问题给出真实入口、条件、执行路径、影响和修复后的验证用例。

严重性：Critical 为可导致大范围数据破坏、服务不可用或关键资产损失；High 为关键链路错误、数据错乱、稳定可触发的资源耗尽等；Medium 为命中必须规则的局部问题（如安全类）。命中必须规则的必须级问题一律阻断；Low 等级及仅风格偏好、无具体证据的问题不写入报告。不要仅凭风格偏好认定严重 bug；对缺上下文且可能严重的问题先补证，无法补证记 `UNKNOWN`。

## 6. 可观测

先判断本次变更是否处于关键链路，例如鉴权、订单/支付、核心数据写入、任务消费、外部关键依赖、关键异步处理。

- 为每条受影响关键链路找到实际可用指标：入口/操作计数及结果标签，或能反映成功失败/积压/延迟的等价业务指标。可以少，但必须能观察其健康状态。
- 允许复用已有指标，要求证明本次新路径经过该埋点、采集器已注册/导出，并能按稳定低基数标签归因；无需每个函数创建指标。
- 检查失败/重试/超时是否计入，避免只在成功出口埋点；检查重要异步环节是否被入口指标遗漏。
- 不把仅有日志、未启用的 metric 定义、无法导出的指标或纯 trace 自动视为业务指标满足要求。
- 缺指标或关键失败结果无法观测设 `FAIL`；无法核实采集路径设 `UNKNOWN`。非关键链路需记录 `NA` 理由。
- 对重复/无使用价值指标、用户 ID/订单 ID/原始 URL 等高基数标签，按推荐级 `METRIC_REDUNDANCY` 列出精简建议（不阻断）；不以“指标太多”本身阻断，若造成明确资源耗尽，另按性能门禁阻断。

## 7. 日志规则

- 识别关键错误：关键业务操作失败、关键依赖失败、数据不一致、任务最终失败、鉴权异常、不可恢复错误等。检查错误传播最终是否在合适责任层记录，避免每层重复打印。
- 日志保留可分析问题的操作名、错误码/错误原因、服务/模块及必要的脱敏对象引用；有请求/异步任务关联时保留 request/trace/task ID。提供字段充分性证据，不强求每条日志同一字段集合。
- 检查关键错误是否被忽略、只有模糊的“failed”、错误字段被覆盖、异步日志无法关联、关闭/退出前日志丢失。
- 缺关键错误日志或缺必要诊断上下文设 `FAIL`；现有统一处理层满足要求时引用其调用路径，不重复加日志。
- 对热循环、每请求大量成功日志、逐条批处理日志、错误重试刷屏，按推荐级 `LOG_REDUNDANCY` 列出采样/限流/聚合/调整级别建议（不阻断）；日志增多本身不阻断，明确 I/O/存储耗尽时按性能门禁阻断。
- 不记录明文密码、完整 Token/Cookie、验证码、支付凭据、密钥或无必要的个人数据；敏感日志按安全门禁阻断，不因“有助分析”豁免。
