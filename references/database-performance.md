# 静态性能、SQL 与业务规则1

## 5.1 静态性能

比较修改前后相同业务请求的复杂度、I/O、并发、锁和资源上界，而不是凭“用了缓存”或“代码更短”判断性能。

- 检查热路径中的 O(n) → O(n²)、循环内 SQL/RPC（N+1）、串行化原有并发、全量扫描/排序、重复序列化、大对象复制、无界结果/队列/goroutine。
- 检查长事务、锁范围扩张、热点锁、连接池耗尽、资源泄漏、重试放大、缓存穿透/击穿/失效，以及取消/超时缺失。
- 记录请求频率、数据规模、每请求查询/远程调用次数、最大分配和锁持有影响。沿依赖及调用方评估影响，不能只看新增函数内部。
- 优先使用已有容量/SLO/基准数据；静态证据足以证明明显退化时设 `FAIL`。是否“明显”无法判定且存在关键热路径高风险时要求受控 benchmark/profile，未验证设 `UNKNOWN`。
- 不虚构延迟比例、QPS 或索引效果，不私自制定性能百分比阈值；低风险微优化不写入报告，有具体证据的调优建议按推荐级 `INDEX_TUNING` 列出（不阻断）。

## 5.2 SQL 与索引

对本次新增/修改 SQL，以及受影响查询路径上的完整最终 SQL（包括 ORM 动态生成、公共 query builder、存储过程调用）建立以下证据表：

| 查询位置/用途 | 数据库版本/表 | WHERE/JOIN/ORDER/GROUP | 实际索引定义 | 可用索引及条件 | 规模/基数 | 计划来源/风险 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- |

执行以下检查：

1. 查找 schema、迁移、索引 DDL 和可信现网 schema 快照；旧迁移不等于现网实际索引。记录适用版本与来源，不依据列名推测“应该有索引”。
2. 对 WHERE、JOIN、排序、聚合、分页和写操作定位对应索引；依数据库规则检查复合索引前缀、等值/范围、排序方向、部分/表达式索引条件、唯一性及选择性。
3. 检查函数/计算包装、隐式类型转换、前导通配符、OR、负向条件、宽范围、大 IN、低选择性、深 OFFSET、SELECT * 和全量聚合是否损害索引效率；这些模式并非在所有数据库都必然失效，基于实际引擎与证据判定。
4. 不把“存在索引”或“计划出现某个 key”视为性能通过。检查预估扫描量、过滤率、回表、排序/临时表、JOIN 基数、返回上界及业务调用频率；索引全扫描也可能明显慢。
5. 可静态证明可用索引且没有明显性能风险时记录推断及限制；优化器是否采用索引存在疑点、动态 SQL 无法还原或热路径风险高时要求授权的脱敏执行计划。优先已有计划/测试环境 `EXPLAIN`，不默认连接现网。
6. 不在现网执行 `EXPLAIN ANALYZE` 或会运行真实语句的诊断；EXPLAIN 也须确认数据库行为与授权。不运行 DML、DDL 或迁移来“验证”。
7. 无任何可用索引或有明确慢查询/性能问题设 `FAIL`；缺 schema/索引/必要计划设 `UNKNOWN`。小表、JOIN 已批准或“以后加索引”不能豁免此规则。纯 DDL/常量 SQL 无数据检索时说明索引匹配不适用，但仍评估 DDL 性能与人工确认。
8. 注意 INSERT/UPDATE/DELETE 的查找条件、唯一约束和索引维护成本；不要要求没有检索条件的 VALUES INSERT 必须命中查询索引。

## 8.1 新表与数据库选择

- 新建表优先使用独立数据库：区分逻辑 database/schema、物理实例及其隔离能力，说明仓库对应概念，并先说明为何独立或为何不独立。
- 复用既有数据库即阻断，建立 `DATABASE_REUSE` 人工确认：表名、目标数据库、为何不独立、访问/容量/备份/运维耦合影响、批准人及时间。
- 未确认复用理由则保持 `PENDING`，不允许合入；不能由 AI 以“看起来合理”批准。
- 使用独立数据库时没有数据库复用关卡，但仍必须完成现网 schema 确认与其他检查。

## 8.2 表结构与现网确认

- 覆盖 CREATE/ALTER/DROP/RENAME TABLE、列/类型/默认值/约束/索引变化，以及 ORM 自动建表、migration DSL、生成 schema 和运行时隐式 DDL。
- 每个新建或修改表都必须建立 `PRODUCTION_SCHEMA` 人工确认，未确认完成即阻断，不允许合入。保守地将删除/重命名视为破坏性表结构变更，不因 SQL 不含 ALTER 而遗漏。
- 要求确认对应环境中的变更已经实际完成并核验：精确数据库/表/变更项、现网环境、完成时间、变更单/执行回执或脱敏 schema 核验、确认人、关联代码版本。
- 不接受“已经提交迁移”“部署时会运行”“计划上线”“CI 测试库已变更”作为现网已变更证据。审查过程中不执行现网 DDL。
- 独立审查前后兼容性：现网 DDL 完成后旧 main 服务仍须可用；滚动发布的新旧代码、约束收紧、非空/默认值、类型变化、索引构建锁和大表迁移均需检查。
- 对破坏性变更明确提醒采用扩展—迁移—收缩/分阶段发布。人工确认已执行 DDL 不豁免兼容性 bug、安全或性能风险。

## 8.3 JOIN 人工确认

- 对候选代码中的 SQL 扫描显式 INNER/LEFT/RIGHT/FULL/CROSS JOIN、逗号隐式连接、ORM join 或关系加载实际 SQL，涵盖新增/修改语句及受影响查询路径。ORM preload 未生成 JOIN 时不误报为 JOIN，但继续评估 N+1。
- 代码中的 SQL 出现 JOIN 即阻断，建立 `JOIN` 人工确认：代码位置/查询标识、关联表、业务目的、是否必须 JOIN、替代方案、为何选此方案、批准人/时间及适用版本；未确认不允许合入，人工明确否定必要性或拒绝批准记 `REJECTED` 并 `BLOCKED`。
- 原来就有 JOIN，但本次修改查询或调用行为影响该 JOIN 路径时同样阻断；无关未修改 JOIN 不做全仓阻断，但不得以“本来就存在”为由跳过本次受影响路径的确认。
- 评论、文档或变量名包含 join 不是 SQL JOIN；疑似动态 SQL 无法还原时记检查证据不足，不仅靠正则下结论。
- 未获明确“必须使用”的人工确认前保持 `PENDING`；人工明确否定必要性或拒绝批准时记 `REJECTED`，总结果 `BLOCKED`，修改方案并重新审查，不能用批准语气填造证据。
- JOIN 获批后继续检查索引、基数、语义、权限与性能。连接条件漏租户或笛卡尔积风险按对应门禁另行阻断。

## 判定对应关系

技术检查通过、但上述确认尚待回答时：将 `business_rules` 记为 `PASS`（规则已识别并已登记全部关卡），在 confirmations 中保留 `PENDING`，总结果为 `NEEDS_CONFIRMATION`（阻断，不允许合入）；人工明确拒绝时记 `REJECTED`，总结果为 `BLOCKED`。若规则识别/执行证据不足则记 `UNKNOWN`；若明确遗漏必要关卡、伪造证据或拒绝遵守规则则记 `FAIL`。任何状态均不能跳过其他技术门禁。
